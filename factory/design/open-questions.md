# Open questions

This file lists the items that the discussion has not decided yet. When an item is decided, write it in `factory/records/decisions/` or `factory/design/GLOSSARY.md`, as its importance requires, and delete it from this file.

## To decide

1. **What the Micro World hides from the agent.** (When: before V2 builds the real world generator. Approach: make it a generator setting, for example `visibility: {state, rules, actionEffects}`, so it is not a one-time decision. V0 uses the simplest world.) There are two options: hide only the world state; or also hide the causal rules and the action effects, so that the agent must find them out. The second option is closer to the goal of "building a worldview", but it is also harder. If the rules are public, T1–T3 are close to a planning problem, and B-sym can win.
2. **Process simplification.** (When: at the start of the formal stage, see ADR 0012.) Proposal: keep reproducibility, experiment isolation, control groups, learning curves and basic statistics (mean, confidence interval). Simplify the secrecy process for the release dataset, the 72-hour stability test, and the formal Alpha/Beta/RC/V1 gates.
3. **How to delete personal data.** (When: before P1 connects World 0, or before Memex is distributed to other people, whichever comes first. See factory/design/security-and-data.md D8.) The Event Log is append-only, but personal data may need real deletion. There are two common approaches. One: store personal data outside the log, and keep only a reference in the event (forgettable payload). Two: give each person an encryption key, and destroy the key to delete the data (crypto-shredding). Some argue that destroying the key alone does not always satisfy the GDPR erasure requirement. At present only synthetic data is used, so this has no effect yet. Note: Decay is a cognitive "no longer believe". It is not data deletion.
4. **Action autonomy: the specific levels.** (When: at the decision gate, when P1 is designed.) ADR 0022 sets the direction: each Action has a risk level (read-only, reversible, irreversible, sends externally, modifies itself). The Policy gives allow / deny / ask for each level. The product default is cautious and opens up step by step as features mature. "Self-modification needs user approval" is a core invariant. Not decided yet: how many levels, which level is the default, how each level treats each risk level, and whether a fast classification model decides which Actions need approval. References: the permission modes of Claude Code, and the approval mechanisms of OpenClaw and Hermes.
5. **Multi-level, multi-point fast and slow thinking.** (When: at the end of the validation stage. Research: factory/records/research/adaptive-depth-2026-10-19.md.) The validation stage keeps the split in two (Fast Path / Slow Path), and makes the contract extensible: depth is an enum value, and meta-judgments such as "should I plan" and "how deep should I think" are different questions for Intuition. Each meta-judgment is written to the Event Log (question, options, choice, Certainty, result). At the end of the validation stage, this data answers "where is the split in two not enough". Candidate approaches: a depth ladder (Pattern → Intuition only → Reasoning without thinking → thinking with a budget → plan first and split into subgoals); a Counterfactual Probe that actively tests necessary and sufficient conditions (change one condition at a time, with several Intuitions in parallel); when the probe result or an actual observation causes Surprise, trigger Escalation (an alternative cause, or a blocking condition) and give the suspect condition to Reasoning; mark Claims formed on the Fast Path as not reviewed; do Calibration separately for each Ontology type; downgrade a Pattern after repeated failures; a separate router or scorer (ADR 0027 allows it; principle 8 decides whether to adopt it). Note: several Intuitions come from the same model and have the same bias. Agreement among them is support, not independent evidence (factory/records/research/harness2-2026-10-27.md).
6. **System 3: offline divergence and recombination.** (When: at the end of the validation stage. Research: factory/records/research/system3-divergent-2026-10-19.md.) It runs offline when the agent is idle. It recombines Experiences and Claims from different domains by their relational structure (conceptual blending, structure mapping). Its output goes into an isolated area and is only a candidate. It must pass Verification before it becomes a low-Confidence Claim or a new Pattern, and it cannot trigger an Action directly. The degree of randomness is a configuration parameter. Following principle 8, first design an experiment that can measure the effect, for example a hidden-rule task modeled on Wagner 2004: after offline recombination, does the rate of rule discovery go up? The terms need a separate category (see GLOSSARY.md). Candidate algorithm: the Propose–Probe–Compose of Harness² (propose several changes, run each once, compare the trajectories and then compose; "keep as is" is also a valid answer), run offline on open cases. It is expensive, so the offline period suits it (factory/records/research/harness2-2026-10-27.md).
7. **Whether and when to adopt Pi / Pi Durable.** (When: in stages. Look at it again before V1 starts, when V2 designs the Reasoning Strategy, when P1 is designed, and when P3 is designed. Research: factory/records/research/pi-durable-2026-10-20.md.) Pi Durable is an experimental TypeScript framework that Earendil released on 2026-10-01, for long-running agents that can recover from crashes: task checkpoints, first-write-wins memos, tools that declare whether they can run again, storage adapters with conformance tests, forks of shared history, and multi-client bootstrapping. Its design is very close to ADR 0005 and 0024. Following "use what already exists", the candidate uses are: in V1, pi-ai for model connections (first verify the parameters that Intuition needs, such as `logprobs`, and record and replay); in V2 or P1, the Pi agent loop for multi-step reasoning on the Slow Path; in P1, Pi Durable for long-running goals; in P3, the MCP and Skills support of Pi. V0 does not introduce it. Questions to solve first: which is the source of truth, its storage or the Event Log; the conflict between resending model requests on recovery and record and replay; how tool-call approval connects to the Policy; whether llama.cpp can connect.
8. **Whether to use Harness²-style harness optimization as a control group.** (When: at the decision gate. Research: factory/records/research/harness2-2026-10-27.md.) Harness² (google-research, arXiv 2610.14224) does not change the model weights. It automatically rewrites the harness and builds an experience library per domain, so that the same model gets better and better in one domain. It has the same success criterion as Memex, by a different route. Someone will ask "how does B3 compare with harness optimization". ADR 0010 requires the experiment matrix of the validation stage to stay minimal, so it is not added in the validation stage. To consider: the cost is very different (it runs about 4k executions per task), so compare at the same reasoning budget; in Memex, its harness changes count as "self-modification" (ADR 0022 supplement), so as a control group it runs automatically only inside experiments.
