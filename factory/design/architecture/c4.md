# Architecture diagrams (C4 model)

This file describes the architecture of Memex with the C4 model. C4 is the layered notation of Simon Brown, from coarse to fine: System Context, Container, Component, Code. This file draws only the first three levels, plus one dynamic diagram that shows how one cognitive step runs. For the integration contracts between modules, see [contracts.md](./contracts.md).

- The diagrams are Mermaid flowcharts, which GitHub renders directly. Each node is labeled with its C4 element type, for example [Person], [Container], [External]. The built-in Mermaid C4 syntax is not used: it is still experimental, and its automatic layout makes link labels overlap when rendered.
- A "Container" in C4 means **a unit that can run or be deployed on its own**, such as a process or a data store. It does not mean a Docker container specifically.
- Status: draft v0. V0 verifies it through implementation, and it is frozen together with the Cognitive Contract at the decision gate.

## Level 2: Container

Which runnable units and data stores make up one Instance.

```mermaid
flowchart TB
  user(["User<br/>[Person]"])
  subgraph inst["Memex Instance [Software System]"]
    cli["memex CLI<br/>[Container: Node.js]<br/>product commands (designed after the decision gate)"]
    web["Web interface<br/>[Container: optional · P3]"]
    runtime["Runtime process<br/>[Container: Node.js / TypeScript]<br/>long-running agent"]
    log[("Event Log<br/>[JSONL + CloudEvents]<br/>only source of truth")]
    kg[("Knowledge store<br/>[Oxigraph WASM, in process]<br/>Worldview projection")]
    cfg[("Configuration<br/>[resource YAML + overlay]")]
  end
  subgraph val["Validation tools [in the repository, not part of the product, ADR 0020]"]
    lab["Lab Runner<br/>[Container: Node.js]<br/>pnpm lab · schedules Experiments · collects reports"]
    worker["Experiment Worker<br/>[Container: one process per Experiment]<br/>same code as the Runtime"]
  end
  dev(["Developer<br/>[Person]"])
  backend["Model Backend<br/>[External]"]
  ext["MCP / OTLP backends<br/>[External · optional]"]

  user -->|commands| cli
  user -->|HTTP| web
  cli -->|start / check| runtime
  dev -->|pnpm lab run| lab
  lab -->|"child process IPC (JSONL)"| worker
  web -->|"HTTP / SSE"| runtime
  runtime -->|append / replay| log
  worker -->|"append / replay (one per Experiment)"| log
  runtime -->|query / project| kg
  runtime -->|read and validate| cfg
  worker -->|read Experiment configuration| cfg
  runtime -->|"OpenAI-compatible HTTP"| backend
  worker -->|inference or replay| backend
  runtime -->|"MCP / OTLP"| ext

  classDef person fill:#08427b,color:#fff,stroke:#052e56
  classDef cont fill:#438dd5,color:#fff,stroke:#2e6295
  classDef db fill:#438dd5,color:#fff,stroke:#2e6295
  classDef ext fill:#999,color:#fff,stroke:#6b6b6b
  class user,dev person
  class cli,web,runtime,lab,worker cont
  class log,kg,cfg db
  class backend,ext ext
```

Main points:

- **The Runtime and the Experiment Worker run the same code.** They differ only in configuration and isolation. So what is verified in experiments is what actually runs.
- **The Knowledge store runs in process by default** (Oxigraph WASM), so it needs no separate deployment. Only when the scale grows does it switch to server mode, which is only a configuration change.

## Level 3: Component (inside the Runtime)

Dotted lines are assembly; solid lines are calls or data flow.

```mermaid
flowchart TB
  subgraph EXT[External]
    BE[(Model Backend)]
    ENVX[Domain / Micro World]
  end
  subgraph CORE["Core components (the framework itself, not replaceable)"]
    ROOT[Composition Root<br/>load configuration · overlay · validate · capability check]
    STATE[Cognitive State<br/>limited by the Cognitive Budget]
    ACT[Action Executor<br/>invariants → Policy → write log → execute]
    LOG[(Event Log<br/>JSONL + CloudEvents)]
    PROJ[Projectors<br/>Worldview · Experience · Trace]
    TEL[Operational telemetry<br/>JSONL logs + OTel]
  end
  subgraph PORTS["Ports + Providers (replaced by configuration)"]
    STRAT[Cognitive Strategy]
    ATT[Attention]
    INT[Intuition]
    REA[Reasoning]
    VER[Verification]
    KNO[Knowledge]
    RET[Retrieval]
    POL[Policy]
    CAP[Capability]
    ENV[Environment]
    COM[Communication]
  end

  ROOT -. assembles .-> STRAT
  COM -->|goals / input| STRAT
  STRAT <-->|read / write| STATE
  STRAT --> ATT
  ATT --> KNO
  ATT --> RET
  STRAT -->|judge| INT
  STRAT -->|reason| REA
  STRAT -->|verify| VER
  STRAT -->|submit| ACT
  ACT -->|authorize| POL
  ACT -->|append| LOG
  ACT -->|execute| CAP
  CAP -->|step| ENV
  ENV --- ENVX
  ENV -->|Observation| LOG
  LOG --> PROJ
  PROJ -->|update projection| KNO
  INT -->|logprobs| BE
  REA -->|generate| BE
```

Rules:

- **The core components** (Cognitive State, Action Executor, Event Log, Projectors, operational telemetry) are the framework's own code and cannot be replaced.
- **The "port + Provider" components** connect through the contracts (ports and adapters architecture) and can be replaced by configuration.
- **Providers do not call each other.** They work together only through the Strategy or the core components. Attention calls Knowledge and Retrieval because the Strategy grants it. These calls go through `StepContext.services` in the contracts, without referring directly to the implementation of another Provider.

## Dynamic diagram: one cognitive step

```mermaid
sequenceDiagram
  autonumber
  participant Env as Environment
  participant Log as Event Log
  participant S as Cognitive Strategy
  participant A as Attention
  participant I as Intuition
  participant R as Reasoning
  participant V as Verification
  participant X as Action Executor
  participant P as Policy
  participant C as Capability

  Env->>Log: Observation (event)
  Log-->>S: updated Cognitive State (through a Projection)
  S->>A: select(state, budget)
  A-->>S: Claims and entities in focus
  S->>I: judge(compact state, questions)
  I-->>S: answer, probability distribution and Certainty for each question
  alt Certainty reaches the threshold (fast path)
    S->>V: verify(candidate action)
  else unsure, contradictory or unfamiliar (slow path)
    S->>R: reason(context, budget)
    R-->>S: conclusion and suggested actions
    S->>V: verify(conclusion)
  end
  V-->>S: pass or reject (with reasons)
  S->>X: submit(Action)
  X->>P: authorize(Action, actor)
  P-->>X: allow, deny or wait for approval (ADR 0022)
  X->>Log: append(Action event)
  X->>C: execute(Action)
  C->>Env: step(action)
  Env-->>Log: new Observation
```

Each step is written to the Event Log as an event, so the whole process can be replayed and audited, and can produce a Trace.
