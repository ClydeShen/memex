# 架构图（C4 模型）

本文件用 C4 模型描述 Memex 的架构。C4 是 Simon Brown 提出的分层画法，从粗到细依次为：System Context、Container、Component、Code。本文件只画前三层，外加一张动态图，展示一次认知步骤的执行过程。模块之间的集成契约见 [contracts.md](./contracts.md)。

- 图用 Mermaid 的 flowchart 绘制，GitHub 可以直接渲染。节点上标注了对应的 C4 元素类型，例如 [Person]、[Container]、[External]。没有使用 Mermaid 自带的 C4 语法：它目前仍是实验性的，而且实际渲染时自动布局会让连线标签互相重叠。
- C4 里的 "Container" 指**可以独立运行或部署的单元**，比如一个进程、一个数据存储，不专指 Docker 容器。
- 状态：草案 v0。它会在 M0 中通过实现来验证，在正式阶段关卡与 Cognitive Contract 一起冻结。

## 第 1 层：System Context

谁在使用 Memex，以及 Memex 依赖哪些外部系统。

```mermaid
flowchart TB
  user(["用户<br/>[Person]<br/>设定目标 · 批准改进 · 配置 · 运行实验"])
  memex["Memex Instance<br/>[Software System]<br/>在 Domain 中建立 Worldview，<br/>结合模型推理完成任务，从经验中学习"]
  backend["Model Backend<br/>[External]<br/>llama.cpp · vLLM · 云端 API"]
  modelsrc["模型来源<br/>[External]<br/>如 Hugging Face"]
  domain["Domain 数据源<br/>[External]<br/>World 0：Git 仓库与文档"]
  mcp["MCP 服务器<br/>[External · M5]"]
  agents["其他 Agent<br/>[External · 未排期]"]
  otel["可观测性后端<br/>[External · 可选]"]

  user -->|"目标 · 审批 · 配置<br/>CLI / HTTP"| memex
  memex -->|"推理<br/>OpenAI 兼容 HTTP"| backend
  memex -->|"下载 + sha256 校验"| modelsrc
  memex -->|"读取资料 · 观察"| domain
  memex -->|MCP| mcp
  memex -->|A2A| agents
  memex -->|OTLP| otel

  classDef person fill:#08427b,color:#fff,stroke:#052e56
  classDef system fill:#1168bd,color:#fff,stroke:#0b4884
  classDef ext fill:#999,color:#fff,stroke:#6b6b6b
  class user person
  class memex system
  class backend,modelsrc,domain,mcp,agents,otel ext
```

## 第 2 层：Container

一个 Instance 由哪些可运行单元和数据存储组成。

```mermaid
flowchart TB
  user(["用户<br/>[Person]"])
  subgraph inst["Memex Instance [Software System]"]
    cli["memex CLI<br/>[Container: Node.js]<br/>init · doctor · up · models pull · lab run · upgrade"]
    web["Web 界面<br/>[Container: 可选 · M5]"]
    runtime["Runtime 进程<br/>[Container: Node.js / TypeScript]<br/>长期运行的 Agent"]
    lab["Lab Runner<br/>[Container: Node.js]<br/>调度 Experiment · 汇总报告"]
    worker["Experiment Worker<br/>[Container: 每个 Experiment 一个进程]<br/>与 Runtime 同一套代码 · 录制 / 回放"]
    log[("Event Log<br/>[JSONL + CloudEvents]<br/>唯一事实来源")]
    kg[("Knowledge 存储<br/>[Oxigraph WASM，进程内]<br/>Worldview 投影")]
    cfg[("配置<br/>[资源 YAML + overlay]")]
  end
  backend["Model Backend<br/>[External]"]
  ext["MCP / OTLP 后端<br/>[External · 可选]"]

  user -->|命令| cli
  user -->|HTTP| web
  cli -->|启动 / 检查| runtime
  cli -->|lab run| lab
  lab -->|"子进程 IPC（JSONL）"| worker
  web -->|"HTTP / SSE"| runtime
  runtime -->|追加 / 重放| log
  worker -->|"追加 / 重放（每个 Experiment 一份）"| log
  runtime -->|查询 / 投影| kg
  runtime -->|读取并校验| cfg
  worker -->|读取 Experiment 配置| cfg
  runtime -->|"OpenAI 兼容 HTTP"| backend
  worker -->|推理或回放| backend
  runtime -->|"MCP / OTLP"| ext

  classDef person fill:#08427b,color:#fff,stroke:#052e56
  classDef cont fill:#438dd5,color:#fff,stroke:#2e6295
  classDef db fill:#438dd5,color:#fff,stroke:#2e6295
  classDef ext fill:#999,color:#fff,stroke:#6b6b6b
  class user person
  class cli,web,runtime,lab,worker cont
  class log,kg,cfg db
  class backend,ext ext
```

要点：

- **Runtime 和 Experiment Worker 运行的是同一套代码**，区别只在配置和隔离方式。所以实验里验证过的东西，就是实际运行的东西。
- **Knowledge 存储默认在进程内运行**（Oxigraph WASM），因此不必单独部署。只有规模变大以后，才换成服务器模式。这只需要改配置。

## 第 3 层：Component（Runtime 内部）

虚线表示装配关系，实线表示调用或数据流。

```mermaid
flowchart TB
  subgraph EXT[外部]
    BE[(Model Backend)]
    ENVX[Domain / Micro World]
  end
  subgraph CORE["核心组件（Framework 自身，不可替换）"]
    ROOT[Composition Root<br/>加载配置 · overlay · 校验 · 能力检查]
    STATE[Cognitive State<br/>受 Cognitive Budget 限制]
    ACT[Action Executor<br/>Policy → 写日志 → 执行]
    LOG[(Event Log<br/>JSONL + CloudEvents)]
    PROJ[Projectors<br/>Worldview · Experience · Trace]
    TEL[运维遥测<br/>JSONL 日志 + OTel]
  end
  subgraph PORTS["端口 + Provider（按配置替换）"]
    STRAT[Cognitive Strategy]
    ATT[Attention]
    INT[Intuition]
    REA[Reasoning]
    VER[Verification]
    KNO[Knowledge]
    RET[Retrieval]
    POL[Policy]
    CAP[Capability]
    ENV[Environment]
    COM[Communication]
  end

  ROOT -. 装配 .-> STRAT
  COM -->|目标 / 输入| STRAT
  STRAT <-->|读写| STATE
  STRAT --> ATT
  ATT --> KNO
  ATT --> RET
  STRAT -->|judge| INT
  STRAT -->|reason| REA
  STRAT -->|verify| VER
  STRAT -->|submit| ACT
  ACT -->|authorize| POL
  ACT -->|append| LOG
  ACT -->|execute| CAP
  CAP -->|step| ENV
  ENV --- ENVX
  ENV -->|Observation| LOG
  LOG --> PROJ
  PROJ -->|更新投影| KNO
  INT -->|logprobs| BE
  REA -->|生成| BE
```

规则：

- **核心组件**（Cognitive State、Action Executor、Event Log、Projectors、运维遥测）是 Framework 自己的代码，不可替换。
- **"端口 + Provider" 组件**通过契约接入（端口与适配器架构），可以通过配置替换。
- **Provider 之间互不调用。** 它们只经由 Strategy 或核心组件协作。Attention 调用 Knowledge 和 Retrieval，是 Strategy 授权它这样做的；这些调用通过契约里的 `StepContext.services` 完成，不直接引用其他 Provider 的实现。

## 动态图：一次认知步骤

```mermaid
sequenceDiagram
  autonumber
  participant Env as Environment
  participant Log as Event Log
  participant S as Cognitive Strategy
  participant A as Attention
  participant I as Intuition
  participant R as Reasoning
  participant V as Verification
  participant X as Action Executor
  participant P as Policy
  participant C as Capability

  Env->>Log: Observation（事件）
  Log-->>S: 更新后的 Cognitive State（经 Projection 得到）
  S->>A: select(state, budget)
  A-->>S: 关注的 Claim 和实体
  S->>I: judge(精简后的状态, 问题)
  I-->>S: 每道题的答案、概率分布和 Certainty
  alt Certainty 达到阈值（快路径）
    S->>V: verify(候选动作)
  else 拿不准、矛盾或陌生（慢路径）
    S->>R: reason(上下文, 预算)
    R-->>S: 结论和建议的动作
    S->>V: verify(结论)
  end
  V-->>S: 通过或驳回（附原因）
  S->>X: submit(Action)
  X->>P: authorize(Action, 执行者)
  P-->>X: 允许或拒绝
  X->>Log: append(Action 事件)
  X->>C: execute(Action)
  C->>Env: step(动作)
  Env-->>Log: 新的 Observation
```

每一步都会以事件的形式写入 Event Log，所以整个过程都可以重放、审计，并能生成 Trace。
