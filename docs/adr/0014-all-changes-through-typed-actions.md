# 所有改动都经过有类型的 Action，记录执行者，并经过策略检查

对 Worldview 的写入、对本体的修改、Capability 的执行，都必须通过一个有名字、有参数结构的 Action 完成，不能直接写入。每个 Action 都会：

- 记录执行者，即 PROV-O 意义上的归属（ADR 0007）。执行者可以是用户、Agent 自身，或者其他 Agent。
- 在执行前经过 `PolicyProvider` 检查。`PolicyProvider` 是可配依赖，默认实现是"全部允许"。
- 作为一条事件写入事件日志（ADR 0005）。

Observation 不是 Action：它记录的是"发生了什么"，直接写入事件日志，不经过策略检查。根据 Observation 形成或修改 Claim，才是 Action。在 MVP 阶段，这个 Action 由运行时以确定性的方式执行。

这套做法参考了 Palantir Foundry：对象默认只能通过 Action 修改，每个 Action 是一次事务，权限分为"能看到这个 Action""能编辑这个 Action""能用某组参数执行这个 Action"，并且可以设定提交条件。

## 为什么现在就需要

即使只有一个用户，这套机制也已经有实际用途。按"自我进化"的定义（ADR 0011），Agent 可以执行"提议修改本体"，只有用户可以执行"批准修改本体"。这本身就是一个包含两种角色的权限模型。

如果一开始没有 Action 这一层，以后要加权限，就得找出所有直接写入的地方逐一改造，代价很高。

## 将来的扩展

多用户、多租户、角色与用户组、对象级的访问控制、管理界面、审计报表，都可以通过新增 `PolicyProvider` 实现或增加界面来完成，不需要改动架构。

目前的部署形态是：每个人运行自己的 Instance，团队之间共享配置、Domain Pack 和策略。这和 Claude Code 的分层设置是同一种思路：个人设置、写进仓库的项目设置、本地覆盖、企业托管策略。
